# 公共问题与上下文协议 v1.0

**项目：** 备课搭子 · 四模块统一教学智能体平台  
**日期：** 2026-10-05（Asia/Shanghai）  
**适用模块：** F1 智能评审、F2 教案生成/优化、F3 课堂模拟、F4 引导修订  
**协议归属：** 统一平台（Lessongen-main）  

## 1. 结论与边界

本协议解决两个问题：

1. 不同模块产生的“问题、证据、建议”采用同一种平台结构保存；
2. 用户从任意模块开始时，平台按当前教案版本动态组装已有上下文，有则使用、没有则跳过，不建立强制固定流程。

本协议不要求 F1–F4 修改各自内部原生结果格式。统一平台负责做适配和保存，原始结果继续保留，以便下载、审计和重新转换。

当前源码已经确认：

- 教案身份由 `lessonId` 标识；
- 不可变教案版本由 `versionId` 标识，并保存 `parentVersionId/contentSha256/sourceModule`；
- F1 任务已绑定 `lessonId + versionId + nativeRunId`；
- F2 优化任务已绑定 `lessonId + sourceVersionId + savedVersionId`；
- F4 已保存 `sessionId + lessonId + sourceVersionId` 及回写版本；
- F3 记录已绑定 `lessonId + versionId + f4SessionId + f3SessionId`；
- 现有 F3 只保存课堂记录和 Markdown 简报，尚未生成正式的结构化实施问题 `issues[]`；
- 现有 F1/F2/F4 的问题字段可以转换，但当前主工程尚无统一问题表和统一上下文查询接口。

因此，本协议是下一阶段实现合同，不把尚未开发的能力描述成已完成。

## 2. 核心原则

### 2.1 版本严格绑定

每个问题必须绑定产生它的 `sourceVersionId`。问题不能只绑定教案而不绑定版本。

- F1 评审 V1：问题属于 V1；
- F2 基于 V1 优化并生成 V2：诊断问题属于 V1，改写结果指向 V2；
- F3 模拟 V2：课堂实施问题属于 V2；
- F4 基于 V2 修订并生成 V3：建议属于 V2，采纳后的正文属于 V3。

切换到新版本后，旧问题仍可查看，但默认标记为 `STALE`，不得静默当作新版本事实。

### 2.2 有来源才进入公共问题层

平台不得根据前端文案、页面状态或模块名称自行推断问题。每条公共问题必须能回到：

- 原生任务/会话 ID；
- 原始结果中的字段或事件；
- 产生问题的教案版本；
- 可选的原文引用、课堂轮次或建议记录。

没有证据的字段使用 `null` 或空数组，不能由适配器编造。

### 2.3 原始结果与标准结果并存

- `rawResult`：模块原始产物，不改写、不丢弃；
- `CommonIssue`：供跨模块读取的标准问题；
- `CommonContext`：一次调用前动态组装的上下文快照。

公共层不是替代各模块，而是模块之间的翻译层。

### 2.4 任意入口、按需读取

F1、F2、F3、F4 均允许独立运行。目标模块启动时查询当前选定版本的上下文：

- 没有其他模块结果：正常独立运行；
- 有适用结果：展示来源并由用户确认是否使用；
- 有旧版本结果：默认不注入，只提示存在旧版结果；
- 用户明确选择跨版本参考时，必须携带版本标识和“旧版本参考”提示。

## 3. 公共问题 `CommonIssue`

### 3.1 JSON 合同

```json
{
  "schemaVersion": "1.0",
  "issueId": "01...ULID",
  "lessonId": "01...",
  "sourceVersionId": "01...",
  "sourceModule": "F1",
  "sourceType": "ANNOTATION_RUN",
  "sourceId": "平台任务ID",
  "nativeSourceId": "模块原生任务或会话ID",
  "category": "objective_measurability",
  "severity": "MEDIUM",
  "status": "OPEN",
  "title": "教学目标缺少可测量表现",
  "description": "目标表述未给出可观察行为与达成条件。",
  "location": {
    "sectionId": null,
    "sectionType": "objectives",
    "sectionTitle": "教学目标",
    "textQuote": "理解一次函数的概念",
    "startOffset": null,
    "endOffset": null
  },
  "evidence": [
    {
      "evidenceType": "DOCUMENT_QUOTE",
      "label": "F1 原文引用",
      "content": "理解一次函数的概念",
      "eventId": null,
      "turnIndex": null,
      "speaker": null
    }
  ],
  "analysis": "目标无法直接支持课堂评价。",
  "suggestedAction": "改为包含行为、条件和达成标准的目标。",
  "target": {
    "sectionId": null,
    "sectionType": "objectives",
    "sectionTitle": "教学目标"
  },
  "dimension": {
    "standardId": "F1-student-V3",
    "level1": "学情与目标分析",
    "level2": "教学目标",
    "score": 3,
    "maximum": 5,
    "grade": "B"
  },
  "confidence": null,
  "resolution": {
    "resolvedInSource": false,
    "resolutionText": null,
    "outputVersionId": null,
    "decision": null,
    "decidedAt": null
  },
  "createdAt": "2026-10-05T00:00:00+08:00"
}
```

### 3.2 必填字段

| 字段 | 规则 |
|---|---|
| `schemaVersion` | v1 固定为 `1.0` |
| `issueId` | 统一平台生成的 ULID；不使用模块内序号冒充全局 ID |
| `lessonId` | 必须是 `platform_lesson.id` |
| `sourceVersionId` | 必须属于该 `lessonId` |
| `sourceModule` | `F1`、`F2`、`F3`、`F4` |
| `sourceType` | 见 3.3 |
| `sourceId` | 统一平台保存的任务/记录 ID |
| `category` | 见 3.4；无法可靠映射时用 `other` |
| `severity` | 见 3.5；来源不提供时用 `UNSPECIFIED` |
| `status` | 见 3.6 |
| `title` | 简短问题名；不能只写“需要优化” |
| `description` | 来源实际表达的问题，不得补造 |
| `evidence` | 可以为空，但若为空必须能通过 `sourceId` 找回原始结果 |
| `createdAt` | 平台入库时间，ISO 8601 |

### 3.3 来源类型

| `sourceModule` | `sourceType` | 已确认的原生来源 |
|---|---|---|
| F1 | `ANNOTATION_RUN` | `platform_annotation_run` 与 F1 `rawResult.维度评分[].批注列表[]` |
| F2 | `OPTIMIZATION_JOB` | `platform_optimize_job_link`、引擎 `implemented_changes/unresolved_issues/review/optimization` |
| F3 | `SIMULATION_RUN` | `platform_simulation_run.result_json`；正式 `issues[]` 尚待开发 |
| F4 | `NAVIGATION_SESSION` | F4 `suggestions[]`、`decisions[]`、session export/current-state |

### 3.4 问题分类

首版沿用 F4 已存在并经过 Pydantic 限制的分类，避免另造一套近义枚举：

```text
missing_component
objective_measurability
learner_analysis
content_accuracy
pedagogical_alignment
activity_design
assessment_alignment
interaction_quality
cross_section_consistency
resource_design
document_quality
other
```

F1 没有稳定提供这些英文分类，因此 F1 适配规则只能进行明确映射；无法确认时必须使用 `other`。F3 将来如需增加 `student_misconception/time_management/participation_imbalance` 等课堂专属分类，应通过协议小版本扩展，不能先在页面写死后倒推数据库。

### 3.5 严重程度

```text
CRITICAL | HIGH | MEDIUM | LOW | UNSPECIFIED
```

- 只有来源明确给出或存在经测试的确定性换算规则时，才能填写前四档；
- F1 的 A/B/C 是维度达成等级，不等于单条问题严重程度，不能直接把 C 换成 HIGH；
- 当前 F2/F4 也没有统一严重度字段，因此首版多数记录应为 `UNSPECIFIED`；
- F3 正式问题生成器可以直接输出严重度，但必须有课堂证据。

### 3.6 状态与解决关系

```text
OPEN | ACCEPTED | REJECTED | RESOLVED | STALE
```

- `OPEN`：尚未处理；
- `ACCEPTED`：教师已接受处理建议，但不代表正文已经成功保存；
- `REJECTED`：教师明确拒绝该建议；
- `RESOLVED`：已有可追溯的输出版本或模拟内解决证据；
- `STALE`：问题属于非当前版本，且未经过新版本重新验证。

禁止仅因生成了新版本就把所有旧问题批量标为 `RESOLVED`。能够证明某问题对应修改已进入 `outputVersionId` 时才可解决；否则保持旧状态并标识版本过期。

## 4. 模块适配规则

### 4.1 F1 → CommonIssue

确定映射：

| F1 字段 | 公共字段 |
|---|---|
| 平台 `lessonId/versionId` | `lessonId/sourceVersionId` |
| 批注任务平台 ID | `sourceId` |
| F1 `runId` | `nativeSourceId` |
| `维度名称` | `dimension.level2` |
| 六个一级维度聚合关系 | `dimension.level1` |
| `得分/满分/等级` | `dimension.score/maximum/grade` |
| `批注列表[].位置` | `location.sectionTitle`（仅作文本位置说明，不冒充 sectionId） |
| `原文引用` | `location.textQuote` 和 `evidence` |
| `具体分析` | `analysis` |
| `建议` 或 `细化建议` | `description/suggestedAction` |

说明：当前 F1 v1.2 的批注等级已改为 A/B/C，但旧样例仍存在中文五档。适配器必须读取实际 v1.2 API 结果，不能拿旧样例值写死。

### 4.2 F2 → CommonIssue

已确认 F2 引擎结果包含：

- `implemented_changes[].critique_id/target_path/summary`；
- `unresolved_issues[]`；
- `optimization`、`review`；
- 平台绑定 `sourceVersionId/savedVersionId`。

映射规则：

- `unresolved_issues[]` 每项可形成一个 `OPEN` 问题；来源没有位置、分类或严重度时保持空值/`other`/`UNSPECIFIED`；
- `implemented_changes[]` 是修改记录，不应单独冒充未解决问题；如能通过同一 `critique_id` 找到对应诊断，可将其标记为 `RESOLVED` 并绑定 `savedVersionId`；
- `content_changed=false` 或保存后 `savedVersionId=sourceVersionId` 时，不得宣称已解决问题。

F2 当前平台启动 DTO 只传 `optimizationFocus` 和 `mustPreserveContent` 等已有字段。公共上下文注入应先组装为摘要，再放入已经允许的文本入口；在核对引擎完整请求合同前，不新增臆测字段。

### 4.3 F3 → CommonIssue

现状：当前 F3 Runner 记录 `materials/rounds/finalState` 并生成简报，但没有经过正式验证的 `issues[]`。因此现在不能从每轮对话自动宣称产生了哪些教学问题。

F3 完整版应新增独立的问题提取结果：

```json
{
  "issues": [
    {
      "nativeIssueId": "ISSUE-01",
      "category": "other",
      "severity": "MEDIUM",
      "problem": "学生容易混淆一次函数与常函数",
      "evidence": [
        {
          "eventId": "evt-...",
          "turnIndex": 6,
          "speaker": "inquisitive_mind",
          "content": "k 等于 0 时是否仍是一种一次函数？"
        }
      ],
      "resolvedInSimulation": true,
      "resolution": "教师在后续对话中进行了区分",
      "suggestedAction": "在新知探究加入 k=0 反例",
      "targetLessonSection": "新知探究"
    }
  ]
}
```

约束：

- `evidence.eventId/turnIndex/content` 必须能在保存的课堂事件中找到；
- 没有证据的问题不能进入公共层；
- `resolvedInSimulation=true` 只表示模拟对话中处理过，不代表教案已修改；
- F3 不产生 `outputVersionId`，发送到 F2/F4 后由修订模块产生新版本。

### 4.4 F4 → CommonIssue

F4 已确认的原生建议字段为：

```text
issue, reason, pedagogical_basis, revision,
issue_type, scope, confidence, revision_mode,
target_text, knowledge_ids
```

确定映射：

- `issue` → `description/title`；
- `reason` → `analysis`；
- `pedagogical_basis` → 证据/依据补充；
- `revision` → `suggestedAction`；
- `issue_type` → `category`；
- `confidence` → `confidence`；
- `target_text` → `location.textQuote`；
- ACCEPT/REJECT → `resolution.decision` 与问题状态；
- F4 回写成功的新版本 → `resolution.outputVersionId`。

## 5. 公共上下文 `CommonContext`

### 5.1 JSON 合同

```json
{
  "schemaVersion": "1.0",
  "contextId": "01...ULID",
  "lesson": {
    "lessonId": "01...",
    "versionId": "01...",
    "versionNumber": 3,
    "contentSha256": "64位sha256",
    "title": "一次函数",
    "subject": "数学",
    "grade": "七年级",
    "topic": "一次函数"
  },
  "targetModule": "F4",
  "requestedAt": "2026-10-05T00:00:00+08:00",
  "selectionPolicy": {
    "sameVersionOnly": true,
    "includeModules": ["F1", "F2", "F3"],
    "includeStatuses": ["OPEN", "ACCEPTED"],
    "maxIssues": 20,
    "maxCharacters": 4000
  },
  "sources": [
    {
      "module": "F1",
      "sourceType": "ANNOTATION_RUN",
      "sourceId": "01...",
      "nativeSourceId": "32位runId",
      "sourceVersionId": "01...",
      "createdAt": "...",
      "summary": "六个一级维度与十二个二级维度评审摘要"
    }
  ],
  "issues": [],
  "teacherConstraints": [],
  "versionLineage": [
    {
      "versionId": "01...",
      "parentVersionId": null,
      "versionNumber": 0,
      "sourceModule": "IMPORT_DOCX"
    }
  ],
  "omissions": [],
  "renderedPromptContext": "供目标模块使用的受限文本摘要"
}
```

### 5.2 组装规则

默认顺序：

1. 校验 `lessonId/versionId` 归属关系；
2. 只查询 `sourceVersionId=versionId` 的结果；
3. 排除目标模块自身本次任务，避免循环引用；
4. 优先 `OPEN`，其次 `ACCEPTED`；`REJECTED/STALE` 默认不注入；
5. 同一来源内保留原始顺序；跨来源按 `createdAt` 新到旧；
6. 去重只能基于稳定来源键或完全相同的规范化内容，不做未经验证的语义合并；
7. 超过字符限制时，按问题为单位截断，不在一句话中间截断；
8. 在 `omissions` 记录被省略数量、原因和来源；
9. 保存本次上下文快照和 SHA-256，便于证明模型当时实际看到了什么。

### 5.3 目标模块输入

| 目标模块 | 输入策略 |
|---|---|
| F1 | 首版仅评当前教案正文；不把其他模块结论混入正式评分，避免污染共同量表 |
| F2 优化 | 可读取当前版本 F1/F3/F4 的开放问题，写入优化要求摘要 |
| F3 模拟 | 主要读取当前教案结构；可读取教师明确选择的待验证问题，但不能让问题摘要替代课堂材料 |
| F4 引导修订 | 可读取当前版本 F1/F2/F3 的开放问题，通过 `metadata.additional_context` 注入，现有上限 4000 字符 |

F1 的正式评分应保持独立：若先把 F2/F3/F4 的结论喂给 F1，可能改变评分基准，导致不同版本间不可比较。因此 v1.0 不给 F1 注入跨模块问题。

## 6. 建议的平台持久化结构（待编码）

### 6.1 `platform_common_issue`

保存问题主记录，至少包含：

```text
id, lesson_id, source_version_id,
source_module, source_type, source_id, native_source_id,
category, severity, status,
title, description, location_json, analysis,
suggested_action, target_json, dimension_json,
confidence, resolution_json,
payload_sha256, created_at, updated_at
```

幂等唯一键建议：

```text
(source_module, source_type, source_id, native_issue_key)
```

其中 `native_issue_key` 必须来自稳定原生标识；来源没有原生 ID 时，使用“来源内路径 + 规范化问题内容”的 SHA-256。不能只用问题文字作为全局唯一键。

### 6.2 `platform_common_issue_evidence`

保存一个问题的多条证据：

```text
id, issue_id, evidence_type, label, content,
event_id, turn_index, speaker, created_at
```

### 6.3 `platform_context_snapshot`

保存真正提交给目标模块的上下文：

```text
id, lesson_id, version_id, target_module,
selection_policy_json, source_refs_json,
context_json, rendered_text, context_sha256, created_at
```

这三张表是建议实现，不是当前数据库中已经存在的表。实际迁移编号必须先读取用户电脑 Flyway 历史；当前工作区最高为 V10，不能直接假设下一版一定是 V11。

## 7. 建议的平台 API（待编码）

```text
GET  /api/platform/lessons/{lessonId}/versions/{versionId}/issues
GET  /api/platform/lessons/{lessonId}/versions/{versionId}/context?targetModule=F4
POST /api/platform/lessons/{lessonId}/versions/{versionId}/context-snapshots
GET  /api/platform/context-snapshots/{contextId}
```

首版不提供任意客户端直接创建问题的公共 POST。问题应由受控模块适配器从已保存的真实结果生成，避免前端伪造来源。

## 8. 错误与一致性规则

| 情况 | 处理 |
|---|---|
| `versionId` 不属于 `lessonId` | 404/业务资源不存在 |
| 目标版本不是当前版本 | 允许查看；启动修改型任务前要求用户明确确认 |
| 来源任务未完成 | 不生成问题，返回来源仍在运行 |
| 原始结果字段缺失 | 保留原始结果，记录适配失败；不生成猜测问题 |
| 来源结果 hash 改变 | 视为来源异常，重新适配需新快照并保留审计 |
| 上下文超过模块限制 | 按完整问题截断，并写入 `omissions` |
| 新版本产生 | 旧问题不删除；默认从当前上下文中排除并标记旧版 |
| 同一个任务重复回调 | 依赖幂等键，不重复创建问题 |

## 9. 最小实施顺序

1. 在最新版 `Lessongen-main` 中加入协议 DTO、数据库迁移和只读查询服务；
2. 先实现 F1 适配器，因为 F1 结构最明确且已有真实结果；
3. 实现 F2 `unresolved_issues/implemented_changes` 适配；
4. 实现 F4 suggestion/decision 适配及 `additional_context` 注入；
5. 完成 F3 正式 `issues[]` 生成后再接入公共层，当前不能用简报冒充；
6. 保存上下文快照，验证 F2/F4 模型真实输入中包含所选问题；
7. 最后做 Web 的问题来源、版本状态、发送到优化/修订页面。

## 10. 验收标准

- 任意一条公共问题都能追溯到模块原始任务、版本和证据；
- V1 的问题不会默认注入 V2；
- 没有 F1/F3 结果时，F2/F4 仍可独立运行；
- F2/F4 使用上下文时，能通过快照证明真实模型输入包含这些问题；
- F3 尚未生成结构化问题时，页面明确显示“暂无实施问题摘要”，不伪造；
- F4 ACCEPT/REJECT 和新版本回写能更新相应公共问题关系；
- 重复适配同一任务不会新增重复问题；
- 原始结果、公共问题、上下文快照三者均可查询；
- Web 能区分“当前版本问题”“历史版本问题”“已解决”“已拒绝”。
